CSIS SmartAssist Project Proposal

A Secure Campus-Wide On-Premise AI Chatbot and Smart Resource Booking System

Problem Statement:

The CSIS department requires a secure, campus-wide AI-powered conversational chatbot framework
to assist faculty, students, and administrative staff. The system must provide instant, accurate
responses to academic and administrative queries while enabling intelligent lab and room booking
through natural language interaction, acting as a single point of interaction to reduce manual
communication overhead.




Description:


CSIS SmartAssist is designed to solve a very common frustration: the time wasted searching for
department information and booking campus spaces. Instead of digging through handbooks,
navigating clunky portals, or waiting on back-and-forth emails, students and staff can simply ask our
secure chatbot a question and get an instant, accurate answer based on official university documents.

Beyond just answering questions, the system actually helps get things done. If a faculty member
needs to reserve a lab or a seminar hall, they can just ask the assistant. The system automatically
checks the calendar for conflicts and sends a quick, one-click approval email to the right
administrator. Most importantly, we've built all of this to run entirely on our own campus servers,
ensuring that the department's internal documents and conversations stay completely private and
secure.




User Roles:

The proposed portal caters to three distinct user roles:

 ●   Admins: They will manage the overall functionality of the portal. They will also manage institution-
     approved documents (PDFs, Excel sheets, Word documents, official circulars) in Google Drive,
     and approve or reject room/lab bookings via a secure email link workflow.

 ●   Faculty Members & Staff: They can seamlessly interact with the AI assistant to retrieve
     academic policies, check TA allocation timelines, and request lab or room bookings using natural
     language.

 ●   Students: Students will be able to check TA form procedures, bill reimbursement workflows, and
     lab access guidelines. They can also view availability for specific labs or rooms and initiate
booking requests.
Key Features

Technical Innovations (Our Unique Approach)

     ● Multi-Agent Semantic Routing (via LangGraph): We use a LangGraph state machine to
        dynamically route queries to either a document retrieval agent or a Calendar booking tool. This
        multi-agent approach prevents the hallucination and prompt brittleness that occurs when
        forcing a single LLM to handle both open Q&A and strict API execution.

     ● Context-Enriched GraphRAG Pipeline: Standard chunking often orphans critical context
        (e.g., separating a deadline from its source document). We programmatically append high-
        level document summaries to vector embeddings before storing them in our graphDB,
        drastically improving semantic search accuracy and modelling of complex relationships.

Core System Capabilities

     ● Desktop-First Conversational UI: We prioritize a Next.js web interface, as faculty and
        students primarily manage academic tasks on desktops. This allows us to rapidly build a
        productive chat UI without the debugging overhead of a cross-platform mobile app.

     ● Automated Booking & Approval Workflow: Integrates with the Google Calendar API for slot
        verification and uses SMTP for single-click email approvals. Keeping faculty in their existing
        email workflow, rather than forcing them to use a separate dashboard, minimizes friction and
        ensures higher adoption.

     ● Secure On-Premise Deployment: Guarantees institutional data privacy by running open-
        source LLMs locally, ensuring no sensitive campus queries or internal documents ever hit
        external web APIs.

Technology Stack

To ensure a user-friendly and interactive interface, we'll utilize a robust stack tailored for AI
integration:

 ●    Frontend: Next.js (React) Prioritizing a desktop-first web interface avoids mobile cross-
      platform debugging overhead. Next.js provides native routing, and React's state management
      efficiently handles a real-time conversational UI without excessive boilerplate.

 ●    Backend API: Flask (Python) Python is required for the LangChain ecosystem. Flask serves as a
      lightweight API router bridging the Next.js frontend and the AI pipeline, avoiding the bloated
      overhead of monolithic frameworks.

 ●    Database & Vector Store: PostgreSQL and Neo4j unify ACID-compliant relational data (user
      sessions, bookings) and vector embeddings (document chunks). This architectural choice
      reduces system complexity, network latency, and makes retrieval faster and more reliable.

 ●    AI & RAG Pipeline: Local LLaMA/Mistral via Ollama + LangChain Local, open-source models
      ensure sensitive campus data remains strictly on-premise. Serving the model via Ollama
      abstracts away CUDA dependencies, exposing a clean REST API for LangChain to query against
      our vectorized documents.

 ●    Integrations: Google Calendar API, Drive API & SMTP The Calendar API natively handles slot
      collisions and timezone logic. SMTP integration enables admins to approve or reject bookings via
      a simple email click, maintaining their existing workflow without requiring a separate dashboard.

Implementation Strategy (Milestones)

We will execute the build in parallel streams, focusing on rapid integration and technical rigor.
Development is structured into the following core milestones:

     ● Milestone 1 (Infrastructure & Data Ingestion): Initialize the PostgreSQL and the Neo4j graph
        database. Fetch the pre-approved institutional documents from the designated Google Drive,
        apply context-enriched chunking, and build a knowledge graph that can be used for retrieval,
        and securely store the embeddings in the vector store.

     ● Milestone 2 (AI Backend & Semantic Routing): Deploy the local open-source LLM using
        Ollama to abstract CUDA dependencies. Build the Flask API endpoints and implement a
        LangGraph multi-agent router. This router is designed as a strict state machine utilizing
        TypedDict for state schema validation, deterministically handling state transitions (edges) to
        direct user intents to specific agent functions (nodes), such as the GraphRag document
        retriever or the Calendar booking tool.

     ● Milestone 3 (Web UI & Network Integration): Develop the desktop-first Next.js frontend.
        Establish network communication with the Flask backend using Server-Sent Events (SSE) for
        unidirectional streaming. We will utilize the browser's native EventSource API and
        TextDecoder to process text chunks incrementally, applying robust network programming
        principles to manage concurrent client connections, handle keep-alives, and ensure stable,
        real-time streaming of the LLM's generation.

     ● Milestone 4 (Workflow Automation & Benchmarking): Implement the Google Calendar slot
        verification and the SMTP email trigger for admin approvals. We will conclude with rigorous
        system benchmarking—profiling concurrent API requests, analyzing socket-level connection
        limits, and monitoring memory utilization to ensure the local LLM deployment remains
        performant under campus-wide load.
Database Schema & Data Architecture
The system utilizes PostgreSQL and Neo4j. (Schema might change based on our requirements)


1. Relational Database (PostgreSQL)
The system utilizes PostgreSQL. This "Single-Store" approach for relational data ensures atomic
transactions between booking records and AI-retrieved context.

User Management & RBAC

   ●   Table: users
   ●   Schema: user_id (PK), email (Unique), full_name, role (Enum: 'Admin', 'Faculty',
       'Student').
   ●   Purpose: Manages identity, authorization levels, SMTP-based approval routing, and enforces
       Role-Based Access Control (RBAC) during chat sessions.

Resource & Booking Engine

   ●   Table: labs_resources
          ○ Schema: lab_id (PK), room_number, capacity, resource_type (Lab/Seminar
              Hall), admin_id (FK to users).
          ○ Purpose: Maps specific labs to the Faculty/Admin responsible for approving requests.
   ●   Table: bookings
          ○ Schema: booking_id (PK), user_id (FK), lab_id (FK), start_time, end_time,
              status (Pending, Approved, Rejected), and google_event_id.
          ○ Purpose: Acts as the source of truth for the Calendar agent to check collisions before
              initiating an API call.


2. Knowledge Base & GraphRAG Pipeline (Neo4j)
Neo4j serves as the unified knowledge engine, modeling structural relationships between institutional
entities while storing dense vector embeddings via native vector indexes (Neo4j 5.x). This allows hybrid
graph-traversal and semantic-similarity queries within a single Cypher statement.

Graph Schema

   ●   Nodes: Document, Section, Chunk, Entity (policies, deadlines, departments, roles),
       Collection (e.g., 'HR Policies', 'Academic Bulletin').
   ●   Relationships: * (:Document)-[:HAS_SECTION]->(:Section)
          ○ (:Section)-[:CONTAINS]->(:Chunk)
          ○ (:Chunk)-[:MENTIONS]->(:Entity)
          ○ (:Entity)-[:RELATED_TO]->(:Entity)
          ○ (:Document)-[:SUPERSEDES]->(:Document)
Vector Embeddings within Neo4j

Each Chunk node stores its embedding directly as a node property.

   ●   Properties: chunk_id, content, embedding (512 or 1024 dims), page_number,
       source_url, and high_level_summary.
   ●   Retrieval Logic: The Collection node scopes vector searches to relevant document
       categories. This enables multi-hop queries (e.g., traversing Entity → Chunk → Section
       → Document) to resolve complex policy questions while ensuring the SUPERSEDES
       relationship prioritizes current data.


3. Conversational Context & Analytics
These components maintain stateful multi-turn dialogue and track system performance.

Chat Sessions

   ●   Table: chat_sessions
   ●   Schema: session_id (PK), user_id (FK), thread_id (LangGraph identifier), created_at.
   ●   Purpose: Enables "Persistent Session State," allowing users to resume booking conversations.

Chat History

   ●   Table: chat_history
   ●   Schema: message_id (PK), session_id (FK), role (User/Assistant), content,
       tokens_used.
   ●   Purpose: Stores actual message exchanges and monitors resource consumption.

Summary of the Architecture
This hybrid architecture ensures that structured booking data remains consistent and ACID-
compliant in PostgreSQL, while the complex, interconnected institutional knowledge is navigated
efficiently via Neo4j’s GraphRAG capabilities.
Known System Limitations

  ● Hardware-Bound Inference Latency: Because we prioritize strict on-premise security,
     deploying open-source LLMs locally introduces compute bottlenecks. Concurrent request
     handling and context-window scaling are strictly bounded by the host machine's VRAM
     capacity and memory bandwidth, which may introduce latency spikes during peak campus-
     wide usage.

  ● Static Corpus Ingestion: The MVP's RAG pipeline relies on batch-processing a predefined set
     of institution-approved Google Drive documents. Live synchronization and real-time vector
     updates via Drive API webhooks are currently out of scope for the 48-hour build.

Future Scope & Extensibility

  ● Persistent Session State: Upgrading the LangGraph state machine from in-memory
     execution to a persistent PostgreSQL checkpointer. This will allow users to safely drop and
     resume long-running conversational threads and booking workflows across multiple days.

  ● Event-Driven Document Sync: Transitioning from static batch ingestion to an event-driven
     architecture using Google Drive webhooks, allowing the system to dynamically chunk and re-
     embed policies the exact moment an administrator modifies them.
